
We use a feature branching strategy to protect the main codebase. A developer creates a separate feature branch, makes changes locally, runs unit tests, and pushes the changes to the remote feature branch. This allows parallel development on separate branches. Before merging into main, we use a pull request for code review and the required checks.

The DevOps lifecycle moves through Plan, Develop, Build, Deploy, Test, Release, and Operate and Monitor. We plan the requirements, develop the code, and build a deployable artifact. For a Java application, building includes compiling, running unit tests, and packaging a JAR file. We deploy it into the target environment, configure it, and test its functionality and performance. After approval, we release it to production, monitor its behaviour, and use feedback to plan improvements. Testing also happens throughout the lifecycle.

For the application flow, we use the following testing process:
1. Unit testing is done on the feature branch in the Development environment, locally before committing and pushing the changes. It checks individual functions or small parts of the code.
2. Functional testing is done using a build from the feature branch, deployed to the QA environment before merging into main. We build, deploy, and test the feature to confirm that it behaves as required.
3. Regression testing is done using a build from the main branch in the QA environment after merging the feature. We build, deploy, and test the combined application to confirm that the changes have not broken existing functionality.
4. Performance and load testing are done in the Stage environment using the approved application artifact built from the main branch. They check how the application behaves under expected traffic and heavier workloads. User acceptance testing in UAT confirms that the application meets business requirements.


The MLOps lifecycle follows a similar approach but includes Data Collection and Preparation, ML Development, Build, Train, Evaluate and Test, Deploy for Inference, and Monitor. We collect and prepare data, develop the processing and training pipeline, and prepare its dependencies. We train the model and evaluate its prediction quality using separate data. An 80/20 split is one example, with 80 percent for training and 20 percent for evaluation. Once approved, we deploy the model for inference and monitor its performance with live data to identify when improvements or retraining are needed.

For MLOps, we use the following testing process:
1. Pipeline validation is done on the feature branch in the Development environment. We build and test the pipeline to check that its steps connect, run correctly, accept input, and produce output. This checks pipeline execution before judging prediction quality. After the required checks and review, we merge the changes into main.
2. Model validation is done in the QA environment using the pipeline code from the main branch and the resulting trained model. We evaluate the model against separate evaluation data to check prediction quality. An example is using 80 percent of the data for training and 20 percent for evaluation.
3. Inference testing is done in the Stage environment after deploying the approved model and serving application associated with the main branch version. It checks that the deployed model receives requests, returns predictions, and connects correctly with other application components.
4. Shadow testing is done in the Production environment using the approved model and serving application associated with the main branch version. The model processes live inputs, but its predictions do not affect customer-facing decisions. This allows us to assess its behaviour with live data before enabling it for users.
Code promotion means moving an application or model through Development, QA, Stage or UAT, and Production, with checks before each promotion. We promote the approved application artifact or model version between environments, keeping track of the source code version used to produce it.
